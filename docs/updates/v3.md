# Sknock v3 — Protocol Specification


Currently in discussions w/myself for a better improved version. No changes will be deployed in less than 3 months

## Context

Sknock v2 was designed as a UDP-based Single Packet Authorization system for
humans using TOTP with a mobile authenticator app. It works well for its
original purpose: a person sends a knock to open a firewall rule on a server
they control.

However, the core cryptographic model — a single 186-byte self-contained
packet with ECIES encryption, forward secrecy, and unlinkable messages — has
properties that are valuable beyond the original use case:

- **IoT devices** that need to authenticate without exposing any ports
- **Machine-to-machine** communication where no human is present to enter a TOTP
- **Offline networks** where there is no internet, no NTP, no clock sync
- **Radio and constrained media** (LoRa, BLE, packet radio, satellite) where
  186 bytes is a natural fit
- **Hostile network environments** where packets must be indistinguishable
  from random noise

v3 restructures the packet to support these use cases while keeping the same
186-byte size and the same ECIES cryptographic envelope.

---

## Problems with v2

### 1. Version bytes are not encrypted

The v2 packet has 4 bytes (`0x00 0x02 0x00 0x00`) appended in cleartext at
the end of every packet:

```
v2 packet:
[32B eph_pub][12B nonce][122B ciphertext][16B GCM tag][0x00 0x02 0x00 0x00]
                                                       ────────────────────
                                                       visible fingerprint
```

This is the only non-random content in the packet. A network observer, IDS,
or DPI system can identify sknock traffic by matching this 4-byte suffix on
UDP packets of exactly 186 bytes.

### 2. TOTP requires a clock and a human

TOTP (RFC 6238) depends on synchronized clocks (±30s tolerance) and is
designed for a human reading a 6-digit code from an authenticator app. This
makes it unsuitable for:

- Devices with no reliable clock source (no NTP, no RTC battery)
- Autonomous machines that must authenticate without human intervention
- Environments where clock drift accumulates over months or years

### 3. Payload field sizes are suboptimal

The v2 payload allocates space poorly for non-human use cases:

```
v2 payload (122 bytes):
[64B UID][6B OTP][8B timestamp][44B rule]
 ──────   ─────                 ──────
 oversized  too small for EC     limited
            signatures
```

- **UID at 64 bytes**: a username like `alice` uses 5 bytes; a machine ID
  like `sensor-07` uses 9 bytes. Most of the 64 bytes are null padding.
- **OTP at 6 bytes**: sufficient for TOTP or HMAC truncation, but an Ed25519
  signature requires 64 bytes.
- **Rule at 44 bytes**: limits the complexity of commands or data that can be
  sent in a single knock.

## v3 Packet Structure

### Outer envelope

The ECIES envelope remains identical in structure. Same cryptographic
properties. Same ephemeral X25519 key per packet. Same AES-256-GCM.

```
v3 packet:
[32B eph_pub][12B nonce][N bytes ciphertext][16B GCM tag]

Minimum: 32 + 12 + 33 + 16 = 93 bytes  (knock with no command data)
Default: 32 + 12 + 126 + 16 = 186 bytes (backward compatible with v2)
Maximum: transport-dependent (no protocol limit)

No cleartext fields. Every byte is random or encrypted.
```

The 4-byte cleartext version marker from v2 is removed. Those bytes move
inside the encrypted payload.

**Result: the entire packet is indistinguishable from random data.** There is
no fingerprint, no magic bytes, no way to identify it as a sknock packet
without the server's private key.

### Variable packet size

The v2 packet was fixed at 186 bytes. This was an artifact of the original
field size choices, not a deliberate design decision. In v3, the packet size
is variable.

The cryptographic overhead is fixed at 60 bytes:

```
32B ephemeral X25519 public key  (required for ECDH)
12B AES-GCM nonce                (required for encryption)
16B AES-GCM authentication tag   (required for integrity)
```

The encrypted payload is variable. Its minimum size is 33 bytes (mode +
version + device_id + auth + counter, with no command field). The command
field grows or shrinks to fill the remaining space.

The receiver determines the payload size from the packet size:
`payload_size = packet_size - 60`.

This enables different packet sizes for different transports:

```
 93 bytes (33B payload) → LoRa SF9-SF12, max range, knock-only (no command)
128 bytes (68B payload) → LoRa SF7-SF8, medium range, short commands
186 bytes (126B payload) → UDP/WiFi, backward compatible, full commands
256+ bytes               → UDP/WiFi/BLE, extended telemetry data
```

For constrained transports like long-range LoRa, a knock with zero command
bytes still authenticates the sender and triggers a preconfigured rule on
the receiver. The knock itself IS the message — "I am alive", "execute
default action", or a rule selected by device configuration rather than
packet content.

### Inner payload (restructured)

The first 3 bytes of the decrypted payload are always:

```
[1B mode][2B version]
```

- **mode**: determines the authentication mechanism and field layout
- **version**: protocol version (0x0003 for v3), enables future evolution

The remaining bytes depend on the mode and the packet size.

### Backward compatibility with v2

During a transition period, the server can distinguish v2 packets from v3:

```
Receive 186-byte packet:
  if bytes[182:186] == 0x00020000 → parse as v2 (version suffix present)
  else → attempt ECIES decrypt, read mode byte → parse as v3
```

This allows v2 clients to keep working while v3 clients are deployed. Once
all clients are upgraded, v2 support can be removed.

## Authentication Modes

### Mode 0x01 — TOTP (human with authenticator app)

This is the direct successor to v2 behavior, for human users with a mobile
authenticator app.

```
Payload (variable, minimum 50 bytes):
[1B mode][2B version][32B uid][6B totp][8B timestamp][Remaining: rule]

mode:       0x01
version:    0x0003
uid:        null-padded UTF-8 string (username)
totp:       6-digit TOTP code (RFC 6238, HMAC-SHA1, 30s period)
timestamp:  uint64 Unix epoch seconds
rule:       null-padded UTF-8 string, fills remaining payload space

At 186-byte packet (126B payload): rule field = 77 bytes
At 256-byte packet (196B payload): rule field = 147 bytes
```

Changes from v2:
- UID reduced from 64 to 32 bytes (sufficient for any username)
- Rule field is variable, grows with packet size (77 bytes at default 186)
- Timestamp validation: ±30 seconds (same as v2)

Server verification:
1. Decrypt ECIES envelope
2. Read mode byte → 0x01 → TOTP mode
3. Look up user by UID
4. Verify TOTP against user's seed (±1 period tolerance)
5. Verify timestamp within ±30s of server time
6. Check nonce dedup
7. Check rule permissions
8. Execute action

### Mode 0x02 — HMAC machine (IoT, autonomous devices)

For devices that authenticate autonomously using a shared seed and a
monotonic counter. No clock required. No human required. Infinite
authentication — the counter never exhausts.

```
Payload (variable, minimum 33 bytes):
[1B mode][2B version][16B device_id][6B hmac][8B counter][Remaining: command]

mode:       0x02
version:    0x0003
device_id:  unique device identifier (UUID or similar, 16 bytes)
hmac:       first 6 bytes of HMAC-SHA256(seed, "sknock-m2m-v1:{counter}")
counter:    uint64 monotonic counter (increments per knock)
command:    null-padded UTF-8 string, fills remaining payload space
            (0 bytes if packet is minimum size — knock-only mode)

At  93-byte packet (33B payload): command field = 0 bytes (knock-only)
At 128-byte packet (68B payload): command field = 35 bytes
At 186-byte packet (126B payload): command field = 93 bytes
```

Authentication mechanism:

```
Device computes:
  full_hmac = HMAC-SHA256(seed, "sknock-m2m-v1:{counter}")
  otp_field = full_hmac[0:6]

Server verifies:
  last_accepted = user.counter
  for c in range(last_accepted + 1, last_accepted + 1 + window):
      candidate = HMAC-SHA256(seed, "sknock-m2m-v1:{c}")
      if candidate[0:6] == received_otp:
          accept, update counter to c
          break
```

Properties:
- **Infinite**: no chain to exhaust, derives OTP on the fly from seed + counter
- **No clock**: uses a monotonic counter, not a timestamp
- **Tolerant of packet loss**: configurable window (e.g., 200) allows skipped
  counters from lost packets
- **48-bit OTP space**: 2^48 possible values per counter position; combined with
  ECIES encryption and rate limiting, brute force is not viable
- **Stateless on device**: device only needs to store seed and current counter

Counter synchronization:

The counter field replaces the timestamp. The server tracks the last accepted
counter value per device. If packets are lost (common with UDP and radio),
the server tries successive counter values up to a configurable window size.

```toml
# Server config for machine mode
[users.sensor-07]
uid = 7
mode = "machine-hmac"
seed = "base32-encoded-seed"
counter = 5000          # last accepted counter
counter_window = 200    # tolerate up to 200 lost packets
```

Desynchronization recovery:

If a device exceeds the counter window (e.g., massive packet loss in a
jammed environment), it cannot re-authenticate without intervention. To
mitigate this:

- **Adaptive window**: the server can increase the window size for devices
  in known-degraded environments
- **Parallel recovery chain**: a device can be provisioned with a secondary
  seed used exclusively for resynchronization requests, advancing at a
  slower rate (e.g., once per day)
- **Physical reprovisioning**: as a last resort, on-site reset with a new
  seed

### Mode 0x03 — EC machine (hostile environments) (Not sure if needed, probably 0x02 is enough)

For devices deployed in environments where physical capture is a realistic
threat. Uses Ed25519 signatures instead of symmetric HMAC. The device holds a
private key (ideally in a secure element); the server holds only the public
key.

```
Payload (variable, minimum 91 bytes):
[1B mode][2B version][16B device_id][64B signature][8B counter][Remaining: command]

mode:       0x03
version:    0x0003
device_id:  unique device identifier (16 bytes)
signature:  Ed25519 signature over (device_id || counter || command)
counter:    uint64 monotonic counter
command:    null-padded UTF-8 string, fills remaining payload space

At 151-byte packet (91B payload):  command field = 0 bytes (knock-only)
At 186-byte packet (126B payload): command field = 35 bytes
At 256-byte packet (196B payload): command field = 105 bytes
```

Authentication mechanism:

```
Device computes:
  message = device_id || counter_bytes || command_padded
  signature = Ed25519.Sign(device_private_key, message)

Server verifies:
  message = device_id || counter_bytes || command_padded
  valid = Ed25519.Verify(device_public_key, message, signature)
```

Properties:
- **Asymmetric**: the server never holds the device's private key
- **Server compromise resistant**: an attacker who compromises the server
  obtains only public keys — they cannot impersonate any device
- **Secure element compatible**: the private key can be generated inside a
  hardware secure element (ATECC608, TPM, etc.) and never leave it. The
  provisioning process only extracts the public key.
- **Provisioning security**: unlike symmetric modes, no secret is ever
  transmitted during provisioning. The device generates its own keypair
  internally; only the public key is exported.

Trade-offs vs mode 0x02:
- Command field is smaller (35 bytes vs 93 bytes) due to the 64-byte signature
- Ed25519 is more CPU-intensive than HMAC-SHA256 (still sub-millisecond on
  most MCUs)
- Requires a secure element to fully realize the physical compromise
  resistance benefit

```toml
# Server config for EC mode
[users.sensor-07]
uid = 7
mode = "machine-ec"
device_pubkey = "base64-encoded-ed25519-public-key"
counter = 12000
counter_window = 200
```

## Compromise Detection

Regardless of mode, v3 introduces counter-based compromise detection.

When the server receives a knock with a counter value that has already been
accepted, this indicates one of two situations:

1. A legitimate replay (nonce dedup handles this — normal)
2. Two entities using the same credentials (clone detection)

If the ECIES envelope is valid (different ephemeral key, different nonce) but
the counter collides with an already-accepted value:

```
Server state: sensor-07 last_counter = 5001
Incoming:     sensor-07 counter = 5001, valid ECIES, valid auth
              but nonce is NEW (not a replay of the same packet)

→ Two different packets, both claiming counter 5001
→ ALERT: possible device clone / credential compromise
→ Action: revoke device, notify operator
```

This converts a silent compromise into an immediate, detectable event.

## Minimum Privilege Enforcement

Each device/user entry can restrict:

```toml
[users.sensor-07]
mode = "machine-hmac"
seed = "..."
allowed_rules = ["report_temp", "report_humidity"]   # only these rules
max_rate = 6                                          # max knocks per hour
```

If a device is compromised, the attacker can only execute the rules that
device was authorized for, at the rate it was authorized for. A temperature
sensor cannot open SSH. A field node cannot issue commands to other nodes.

## Transport Independence

The v3 packet is a self-contained blob with no transport-layer assumptions.
It contains no IP addresses, no port numbers, no protocol headers. The only
requirement is a medium that can deliver the packet bytes from sender to
receiver.

Variable packet size allows the protocol to adapt to transport constraints:

| Transport | Max payload | Min sknock packet | Full sknock (186B) | Range |
|-----------|------------|-------------------|-------------------|-------|
| UDP/IP | unlimited | 93B ✓ | 186B ✓ | internet |
| LoRa SF7 (EU) | 222 bytes | 93B ✓ | 186B ✓ | 5-15 km |
| LoRa SF9 (EU) | 115 bytes | 93B ✓ | 186B ✗ | 10-20 km |
| LoRa SF12 (EU) | 51 bytes | 93B ✗ | 186B ✗ | 20+ km |
| BLE | 512 bytes | 93B ✓ | 186B ✓ | ~50m |
| AX.25 | 256 bytes | 93B ✓ | 186B ✓ | 100+ km |
| HF radio | variable | 93B ✓ | 186B ✓ | 1000+ km |
| Iridium SBD | 340 bytes | 93B ✓ | 186B ✓ | global |
| Meshtastic | ~200 bytes | 93B ✓ | 186B ✓ | multi-hop km |

Note: LoRa SF12 (51-byte max) cannot carry even the minimum 93-byte packet.
For extreme long-range LoRa, a future ultra-compact mode with a smaller
cryptographic envelope may be explored.

The sknock codebase will be restructured to separate the cryptographic core
from the transport layer:

```
sknock-core:    BuildPacket() / ParsePacket() — pure crypto, no I/O
sknock-udp:     current UDP transport (sknock, sknockd)
sknock-*:       future transports (LoRa, BLE, etc.)
```

The `internal/spa` package (`packet.go`) already has minimal coupling to the
transport layer. The restructuring formalizes this separation.

## Packet Comparison: v2 vs v3

```
v2 (current, fixed 186 bytes):
[32B eph_pub][12B nonce][122B ciphertext][16B tag][4B version_CLEARTEXT]
                         └─[64B uid][6B otp][8B ts][44B rule]

v3 mode 0x01 TOTP (variable, shown at 186 bytes):
[32B eph_pub][12B nonce][126B ciphertext][16B tag]
                         └─[1B mode][2B ver][32B uid][6B totp][8B ts][77B rule]

v3 mode 0x02 HMAC (variable, shown at minimum 93 bytes and default 186 bytes):
[32B eph_pub][12B nonce][33B ciphertext][16B tag]          ← 93B, knock-only
                         └─[1B mode][2B ver][16B dev_id][6B hmac][8B ctr]

[32B eph_pub][12B nonce][126B ciphertext][16B tag]         ← 186B, with command
                         └─[1B mode][2B ver][16B dev_id][6B hmac][8B ctr][93B cmd]

v3 mode 0x03 EC (variable, shown at 186 bytes):
[32B eph_pub][12B nonce][126B ciphertext][16B tag]
                         └─[1B mode][2B ver][16B dev_id][64B sig][8B ctr][35B cmd]
```

Summary of changes:

| | v2 | v3 |
|---|---|---|
| Total packet size | 186 bytes (fixed) | 93-256+ bytes (variable) |
| Encrypted payload | 122 bytes (fixed) | 33-196+ bytes (variable) |
| Cleartext fingerprint | 4 bytes (version) | none |
| Auth modes | TOTP only | TOTP, HMAC, Ed25519 |
| Clock required | yes | TOTP mode only |
| Human required | yes | TOTP mode only |
| Max rule/command | 44 bytes | transport-dependent (0-93B at 93-186B packet) |
| Machine-to-machine | not supported | modes 0x02 and 0x03 |
| Compromise detection | none | counter collision alerting |
| Transport assumption | UDP | none (transport-agnostic core) |

## Cryptographic Properties (unchanged from v2)

These properties are inherent to the ECIES envelope and remain identical in v3:

| Property | Mechanism |
|----------|-----------|
| Confidentiality | AES-256-GCM |
| Authenticity | GCM authentication tag |
| Forward secrecy | Ephemeral X25519 per packet |
| Unlinkability | Different ephemeral pubkey per packet |
| Replay protection | 12-byte random nonce + server-side dedup |
| Observer sees | 186 bytes of random-looking data (v3: no exceptions) |

## Implementation Plan

### Phase 1: Core restructuring

- Move version bytes inside encrypted payload
- Add mode byte to payload parsing
- Refactor `internal/spa/packet.go` to support multiple payload layouts
- Maintain v2 backward compatibility during transition

### Phase 2: HMAC machine mode (0x02)

- Implement `internal/auth/hmac.go` — HMAC-SHA256 counter-based verification
- Add `machine-hmac` user mode to `internal/config/users.go`
- Add counter tracking and window logic to server
- Add counter collision detection (compromise alerting)

### Phase 3: EC machine mode (0x03)

- Implement `internal/auth/ec.go` — Ed25519 signature verification
- Add `machine-ec` user mode to config
- Document secure element provisioning workflow

### Phase 4: Transport abstraction

- Extract `sknock-core` as a standalone package (BuildPacket/ParsePacket)
- Refactor current UDP transport to use the core package
- Document the packet spec for implementation in other languages (C, Rust)

## Threat Model Updates for v3

New threats addressed:

| Threat | v2 | v3 |
|--------|----|----|
| Traffic fingerprinting via version bytes | vulnerable | mitigated (no cleartext) |
| Device compromise (seed extraction) | not applicable | mode 0x03 + secure element |
| Server compromise → device impersonation | not applicable | mode 0x03 (asymmetric) |
| Credential cloning undetected | no detection | counter collision alerting |
| Privilege escalation via compromised device | no restriction | per-device rule allowlist |

Remaining limitations (not addressed by v3):

| Limitation | Reason |
|------------|--------|
| Physical device capture with unlimited lab resources | Fundamental to all embedded systems |
| Jamming / physical-layer denial of service | Transport-layer problem, not protocol-layer |
| Counter desynchronization beyond window | Requires physical intervention or recovery chain |
| IP address visible at network layer (UDP mode) | Inherent to IP; mitigate with VPN/Tor |
| Unidirectional — no delivery confirmation | By design; mitigate with redundant sends |
